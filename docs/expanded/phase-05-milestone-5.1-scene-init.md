# Phase 5 — Milestone 5.1: Scene Initialization (Expanded)

**Goal:** Establish a single, canonical, correctly-parameterized Three.js scene bootstrap for WordWeaver per §5.2 — `WebGLRenderer` (antialias, pixel-ratio capped at 2), a `PerspectiveCamera` sized for the year overview, a defined lighting rig, a WebGL-support guard with graceful 2D fallback, one persistent animation loop, resize handling, and bus-driven lifecycle — while reconciling the **two independent scenes that already exist** (`src/scene.js`'s viewport scene driving `CalendarApp`, and `WordWeaverScene` with its own canvas/renderer/loop) and the **duplicate event-bus** the 3D stack runs on. This milestone is scene *plumbing only*; the year layout it kicks off (`createYearLayout`) is detailed in 5.2.
**Spec alignment:** §5.1 (3D world powered by Three.js, rendered in a `<canvas>` that fills the viewport behind the UI shell; **scene persists in memory as long as the app is open — not destroyed when switching to 2D**, lines 476–478), §5.2 (Scene Initialization: the 9-step sequence — `WebGLRenderer` antialias+alpha, `pixelRatio = min(dpr, 2)`, `PerspectiveCamera` FOV 60 / near 0.1 / far 1000, year-overview camera offset, Ambient 0.4 + Directional 0.8 + Hemisphere 0.3, `createYearLayout()`, start RAF, resize handler — **and the WebGL fallback: detect support, else set `calendarMode="2d"`, one-time notice, skip 3D**, lines 480–496), §2.3 (Rendering Systems: Three.js r152 minimum, scene root `WordWeaverScene.js`, `WebGLRenderer` antialias, pixel ratio capped at 2.0, lines 143–148), §3 line 77 (mode transitions animate: 3D→2D fades the Three.js canvas out / 2D→3D reverses, 400 ms ease; **both systems stay instantiated in memory, only visibility changes**), §11 line 1005 (architecture tree: `WordWeaverScene` is "3D, **always mounted, hidden in 2D mode**", over a Three.js Canvas), §13.2 (event catalog: `initialized {eventCount}`, `eventCreated/eventUpdated/eventDeleted`, `starterDataCleared` are consumed by `WordWeaverScene`; it emits `dayFocused/weekFocused/monthFocused`, lines 1160–1169), line 436 (`navigateTo` dispatched via the event bus, listened for by **both** `WordWeaverScene.js` (3D) and `Calendar2D.js` (2D)), §2.3 read-only contract (3D scene reads event data exclusively from the timeline model).
**Sequencing:** First milestone of Phase 5 and the foundation the rest stand on — 5.2 (year layout) is literally step 7 of the §5.2 sequence and cannot be specified until scene/camera/lighting ownership is settled here; 5.3 (DayBlock3D) and 5.4 (AtomGlyph3D) populate the scene this milestone creates; 5.5 (camera) deepens the camera/controls stubbed here; 5.6 (interaction) builds on the raycaster/pointer plumbing this scene already wires. Like Phase 4, every task is **grounded against existing code** (reconcile built / gap / next-step, not greenfield) — and Phase 5 inherits Phase 4's recurring finding that the calendar surfaces run on `window` events / a side bus rather than the §13.2 Phase-2 bus, now sharper because the 3D stack ships a **literal second `EventBus.js`**.

## Current implementation status (reconciliation)

The single biggest fact for all of Phase 5: **the spec's "one `WordWeaverScene.js` that fills the viewport and is the 3D scene" does not exist as described. There are two separate Three.js scenes**, neither of which is the persistent-viewport 3D-mode scene §5.1/§11 describe:

- [`createScene(canvas)`](../../src/scene.js) (scene.js:42–203) is the **live viewport scene** — it owns `#three-canvas` (index.html:27), is constructed once in [`main.js`](../../src/main.js) (main.js:30), and hosts `CalendarApp` (main.js:32). Its RAF loop lives in `main.js` (`animate()`, main.js:44–51), externally driven. This is the scene that actually fills the viewport — but it renders the **calendar wall**, not a WordWeaver year ring.
- [`WordWeaverScene`](../../src/wordweaver/WordWeaverScene.js) (1085 lines) is a **self-contained satellite scene**: it creates its **own** `<canvas>` inside a passed container (WordWeaverScene.js:43–46), its own `WebGLRenderer` (64–68), camera (53–56), `OrbitControls` (71–77), lights (79–88), and **auto-starts its own RAF in the constructor** (166). It is instantiated on demand — by the WordWeaver app window ([`apps/wordweaver/index.js`](../../src/apps/wordweaver/index.js):66, `new WordWeaverScene(canvasWrap)`) and by [`WordWeaverEmbed`](../../src/wordweaver/WordWeaverEmbed.js) inside `CalendarApp` — and is **`dispose()`-d on close** (WordWeaverScene.js:751+, `cancelAnimationFrame` + listener teardown). It **does** call `createYearLayout(this.scene, getInitialNotes())` (158) and mount the nested `Timeline3DScene` viewport (144). It is the closest thing to the spec's `WordWeaverScene.js`, but it is a **mounted-on-demand embed, not the always-mounted viewport**.

So Phase 5 is fundamentally a **convergence story**, exactly echoing Phase 4's two-week-renderer situation. Headline deltas vs. §5.1/§5.2:

- **No single canonical scene (architectural):** §11 says `WordWeaverScene` is *always mounted, hidden in 2D*. Reality: the viewport scene is `scene.js` (calendar wall) and `WordWeaverScene` is a disposable embed. 5.1.1 must pick the convergence target before any parameter can be "fixed."
- **Three.js is CDN-loaded via an import map, not npm:** `three` is **absent from `package.json`** (only `@tauri-apps/cli` + `serve`); every module does a bare `import * as THREE from "three"` / `"three/examples/jsm/..."`, resolved by an **import map → unpkg** (`three@0.164.0`, index.html:519–525). 0.164 > the §2.3 r152 minimum ✓, but this is a hard network dependency with no vendoring/SRI — a real concern for `serve:pwa` offline and the Tauri build (5.1.10).
- **No WebGL support detection / fallback anywhere (spec-mandated, fully missing):** §5.2 requires detecting WebGL before init and, if absent, forcing `calendarMode="2d"` + a one-time notice + skipping 3D. **Neither** `createScene` nor `WordWeaverScene` guards `new THREE.WebGLRenderer(...)` — it will throw on unsupported/blocked WebGL with no graceful path (5.1.3).
- **Camera parameters diverge from spec, and one is an outright bug:** §5.2 says FOV 60 / near 0.1 / far 1000. `scene.js` uses 52 / 0.1 / **200** (scene.js:60–65); `WordWeaverScene` uses 42 / 0.1 / **80** (WordWeaverScene.js:53). The far plane of 80 **equals** the §5.3 year-ring radius (80 units) — so the camera literally cannot see the far side of the ring (diameter 160 ≫ far 80). 5.1.4 reconciles params and fixes the far/ring relationship.
- **Renderer `alpha` is `false`, but §5.2 step 1 says alpha enabled — and the fade needs it:** both renderers pass `alpha: false` (scene.js:51, WordWeaverScene.js:67). §3 line 77 requires the 3D canvas to **fade out** during 3D→2D; a transparent (alpha) buffer is what lets the canvas cross-fade cleanly over the DOM grid. 5.1.2 reconciles (tech-stack line 148 only mandates antialias, so this is a genuine spec-vs-code decision).
- **Lighting rigs differ from spec and from each other:** §5.2 = Ambient 0.4 + 1 Directional 0.8 + Hemisphere 0.3. `scene.js` runs a much richer 6-light rig (Hemi 0.55, Ambient 0.35, key Dir 1.05, rim Dir 0.45, fill Point 0.5, warm Point 0.15; scene.js:77–99) plus `FogExp2`; `WordWeaverScene` runs Ambient 1.15 + key Dir 1.25 + rim Point 0.85 and **no hemisphere** (WordWeaverScene.js:79–88), with `scene.fog = null`. 5.1.5 reconciles to a defined rig (the spec values are a floor, not necessarily the ceiling).
- **Two RAF loops / two WebGL contexts can run at once:** `WordWeaverScene` starts its own RAF in the constructor (166) **in addition to** `main.js`'s loop for `scene.js`. When the embed is open, two GL contexts render simultaneously. `WordWeaverScene._tick` *does* already gate the actual `renderer.render(...)` and layout/camera updates on `getCalendarMode() === "3d"` (WordWeaverScene.js:734–746) — good instinct — but it never stops the RAF or releases its context. 5.1.6 reconciles loop ownership.
- **Scene is destroyed, not hidden, on mode/window change:** §5.1/§11 require persist-in-memory + visibility-only toggling with a 400 ms fade. `WordWeaverScene.dispose()` fully tears down (cancel RAF, remove listeners, dispose sub-systems; WordWeaverScene.js:751+) and the embed re-instantiates on reopen. 5.1.8 converges on hide/show.
- **The 3D stack runs on a *second*, duplicate event bus and ignores the §13.2 catalog:** there are **two** bus modules — [`src/utils/EventBus.js`](../../src/utils/EventBus.js) (the Phase-2 bus) and [`src/wordweaver/EventBus.js`](../../src/wordweaver/EventBus.js) (a minimal duplicate: `on/off/emit` over a `Map`). `WordWeaverScene` imports the **wordweaver** one (WordWeaverScene.js:10) and subscribes only to **`timelineUpdated`** (156) — **not** the §13.2 `initialized / eventCreated / eventUpdated / eventDeleted / starterDataCleared`, and it emits **no** `dayFocused/weekFocused/monthFocused`. Mode changes flow through a standalone [`calendarMode.js`](../../src/wordweaver/calendarMode.js) store (`getCalendarMode/setCalendarMode/onCalendarModeChange`), not a §13.2 `modeChanged`/`navigateTo` event; `WordWeaverScene` even reaches over to call `cal2d.hide()/show()` directly (WordWeaverScene.js:191–192). 5.1.9 is the bus convergence — the recurring Phase-4 gap, now a literal duplicate to retire.
- **What's already right (keep):** `pixelRatio = Math.min(devicePixelRatio, 2)` in both (scene.js:53, WordWeaverScene.js:69) matches §2.3/§5.2 exactly; `WordWeaverScene` already reads events only from `timelineModel.js` (§2.3 read-only ✓), already calls `createYearLayout` at init (step 7 ✓), already registers resize + a `ResizeObserver` (WordWeaverScene.js:136–142, more than the spec's bare resize handler), and already mode-gates its render. The bones of §5.2 exist in `WordWeaverScene`; this milestone hardens and de-duplicates them.

- **Implementation notes:** Recommended target — promote `WordWeaverScene` to the canonical *3D-mode* viewport scene (it already does year layout + timeline + mode-gated render + read-only model access), mounted **once** behind the UI shell and toggled by `calendarMode`, and reclassify `scene.js`'s calendar-wall scene as either the legacy/calendar-wall surface or fold its richer lighting/fog into `WordWeaverScene`. Keep `apps/wordweaver/index.js`'s use of `WordWeaverScene` as a *segment* window distinct from the *year* viewport, or unify under one instance with a layout mode — call this out explicitly so 5.2 knows whether year + segment share an instance.
- **Edge cases:** `CalendarApp` already constructs `scene.js` at boot (main.js:30) and embeds `WordWeaverScene` (WordWeaverEmbed); changing ownership must not leave two viewport canvases stacked; embedded (`?embedded`) mode (main.js:10–13) must still pick exactly one scene.
- **UI/UX considerations:** Only one 3D surface should ever be visible behind the shell; the satellite day-weave window (if kept) is a distinct, clearly-framed sub-experience, not a second viewport.
- **Data flow notes:** Whichever scene is canonical is the §13.2 consumer of `initialized/eventCreated/...` (5.1.9) and the emitter of `*Focused` — the decision here fixes *who* subscribes.
- **Testing notes:** After the decision, exactly one full-viewport WebGL context exists in 3D mode (assert via `renderer.info` / a single canvas behind the shell); the retired/!repurposed path no longer creates a second viewport.
- **Performance notes:** Collapsing to one viewport context is itself the biggest perf win in this milestone (see 5.1.6 — two contexts today).
- **Mobile vs desktop:** Same canonical scene both; mobile just swaps controls (5.5) — not a second scene.
- **Integration points:** §2.3 line 144, §5.1, §11 line 1005, and every subsequent 5.1 task.
- **Status:** **Divergent / undecided** (two scenes, neither matching the spec's role). **Next:** record the convergence target (recommend: `WordWeaverScene` as canonical 3D-mode viewport) before touching parameters.

## 5.1.2 — `WebGLRenderer` creation & parameters (antialias, alpha, pixel-ratio cap)

- **Purpose:** Standardize renderer construction on the canonical scene to the §5.2/§2.3 contract and resolve the `alpha` divergence the 3D↔2D fade depends on.
- **Dependencies:** 5.1.1 (which scene); §5.2 step 1–2, §2.3 line 148.
- **Acceptance criteria:** Canonical renderer is `new THREE.WebGLRenderer({ canvas, antialias: true, alpha: <decided> })` with `setPixelRatio(Math.min(window.devicePixelRatio, 2))`; the `alpha` choice is documented and consistent with the 5.1.8 fade approach; tone-mapping/shadow settings (currently scene.js:55–58 only) are decided for the canonical scene.
- **Implementation notes:** `pixelRatio = Math.min(devicePixelRatio, 2)` already matches in both (scene.js:53, WordWeaverScene.js:69) — keep verbatim. The decision is `alpha`: §5.2 step 1 says *alpha enabled*; both renderers use `alpha:false` (scene.js:51, WordWeaverScene.js:67). If the fade (5.1.8) cross-fades the canvas *opacity* over the DOM grid, `alpha:false` + CSS opacity is acceptable; if the grid must show *through* the canvas mid-fade, `alpha:true` is required. Recommend `alpha:true` to honor the spec and keep the fade option open, accepting the minor fill cost. Carry over `scene.js`'s `ACESFilmicToneMapping` + `PCFSoftShadowMap` only if the WordWeaver look wants them (it currently sets none).
- **Edge cases:** `devicePixelRatio` changing across monitors (re-clamp on resize, 5.1.7); `alpha:true` with a `scene.background` set defeats transparency — if alpha is chosen, background must be `null` (WordWeaverScene already sets `scene.background = null`, WordWeaverScene.js:49) or a CSS backdrop.
- **UI/UX considerations:** Capped pixel ratio protects retina/4K perf; antialias on keeps glass-panel edges (§5.4) clean.
- **Data flow notes:** None (pure renderer config).
- **Testing notes:** `renderer.getPixelRatio() <= 2` on a 3×-DPR device; `renderer` constructs without throwing on supported hardware (unsupported path → 5.1.3); with the chosen `alpha`, the 3D→2D fade shows the grid correctly.
- **Performance notes:** Pixel-ratio cap is the primary fill-rate guard; `alpha:true` adds a small per-pixel cost — acceptable.
- **Mobile vs desktop:** Cap matters most on high-DPR phones; same code path.
- **Integration points:** §5.2 (steps 1–2), §2.3 line 148, 5.1.8 (fade), 5.1.7 (resize re-clamp).
- **Status:** **Partial** (pixel-ratio cap ✓; `alpha` diverges from spec). **Next:** decide `alpha` against the fade design and unify renderer construction on the canonical scene.

## 5.1.3 — WebGL support detection + graceful 2D fallback + one-time notice

- **Purpose:** Implement the §5.2 **WebGL Fallback** that is entirely missing today, so a device/browser without WebGL drops to 2D cleanly instead of throwing during `new WebGLRenderer`.
- **Dependencies:** 5.1.1, 5.1.2; `calendarMode.js` (`setCalendarMode`); the §13.2/notification surface used by Alerts (Phase 2).
- **Acceptance criteria:** Before constructing the renderer, WebGL availability is detected; if unavailable, `calendarMode` is forced to `"2d"`, a **one-time** user-facing notice is shown, and **3D init is skipped entirely** (no renderer, no RAF) — the 2D calendar remains fully functional; if available, init proceeds normally.
- **Implementation notes:** Add an `isWebGLAvailable()` probe (create a throwaway `<canvas>`, attempt `getContext("webgl2") || getContext("webgl")`, wrap in try/catch) — Three.js ships `WebGL.isWebGLAvailable()` in `examples/jsm/capabilities/WebGL.js`, importable via the existing `"three/"` import-map entry, so prefer that over a hand-roll. Gate the entire canonical-scene bootstrap behind it. The "one-time" flag persists via the same storage/flags layer Phase 1 established (don't re-notify every load). Forcing `"2d"` must go through `setCalendarMode("2d")` (calendarMode.js:41) so the rest of the app reacts.
- **Edge cases:** WebGL present but context creation later fails/blocked (extension, GPU blocklist) → treat like unavailable at init; context **lost after** successful init is a *runtime* concern handled in 5.1.10; headless/SSR/test (`window`/`document` absent) must no-op, not crash; user manually toggling to 3D after a fallback (block it or re-probe).
- **UI/UX considerations:** Notice is informative, not alarming ("3D view isn't available on this device — showing the 2D calendar"), dismissible, shown once.
- **Data flow notes:** Probe → (fail) `setCalendarMode("2d")` + notify + return; (pass) continue. No timeline reads involved.
- **Testing notes:** With WebGL stubbed unavailable, no renderer/RAF is created, mode is `"2d"`, notice fires exactly once across reloads, 2D calendar works; with WebGL available, 3D inits normally and no notice fires.
- **Performance notes:** Negligible (one throwaway context probe at boot); saves the cost/crash of a doomed renderer.
- **Mobile vs desktop:** Especially relevant on low-end/older mobile and locked-down browsers.
- **Integration points:** §5.2 (WebGL Fallback), `calendarMode.js`, Phase-2 notifications, Phase-1 one-time flags.
- **Status:** **Missing** (no detection or fallback in either scene — `new WebGLRenderer` is unguarded). **Next:** add `isWebGLAvailable()` guard around the canonical bootstrap with `setCalendarMode("2d")` + one-time notice.

- **Integration points:** §5.2 (steps 3–4), §5.3 (ring radius, 5.2), §5.5 (camera framing).

## 5.1.5 — Lighting rig reconciliation (Ambient + Directional + Hemisphere)

- **Purpose:** Define one lighting rig for the canonical scene that meets §5.2's floor (Ambient 0.4 + Directional 0.8 + Hemisphere 0.3) and supports the §5.4 clean glass-panel look — reconciling the two different existing rigs.
- **Dependencies:** 5.1.1; §5.2 steps 5–6; §5.4 material expectations (`MeshPhysicalMaterial`, transmission).
- **Acceptance criteria:** Canonical scene has at minimum an `AmbientLight`, one `DirectionalLight` (top-right-front), and a `HemisphereLight` (pale-blue sky / dark-grey ground) per §5.2; intensities are documented; the rig produces the "clean glass" look (§5.4) with **no** cracked/fracture/distortion effects (§ line 530, 971).
- **Implementation notes:** `WordWeaverScene` currently has Ambient 1.15 + key Directional 1.25 + rim Point 0.85 and **no hemisphere** (WordWeaverScene.js:79–88); `scene.js` has the fuller cinematic rig + `FogExp2` (scene.js:77–107). The spec values are a *floor*; recommend: keep the directional key, **add the missing `HemisphereLight`** for soft fill per §5.2 step 6, and tune ambient down toward spec so transmissive glass (§5.4 `transmission:0.7`) reads (too much ambient washes out transmission). Preserve `WordWeaverScene`'s layer scheme (ENV_LAYER 0 / CONTENT_LAYER 1, WordWeaverScene.js:26–27, 84–87) — lights must `enable` both layers (as they already do at 84–87) or the GLB environment + content won't both light. - **UI/UX considerations:** Lighting sets the "spatial landscape" mood (§5.1); avoid blown highlights on glass; keep within the no-cracked/clean constraint (§ line 971).
- **Data flow notes:** None.
- **Testing notes:** Scene contains Ambient + Directional + Hemisphere; DayBlock glass panels (5.3) read as clean glass under the rig; no banding/wash-out; shadows (if enabled) gated by perf flags.
- **Performance notes:** Hemisphere + ambient + one directional is cheap; **shadows are the expensive choice** — gate via `isHighPerformance()` (perfFlags.js) as `scene.js` patterns already suggest.
- **Mobile vs desktop:** Disable/soften shadows on mobile; same light set.
- **Integration points:** §5.2 (steps 5–6), §5.4, § line 971, `perfFlags.js`.
- **Status:** **Partial / divergent** (has Ambient+Directional but **no Hemisphere**; intensities differ from spec and between the two scenes). **Next:** add `HemisphereLight`, tune intensities toward the spec floor, decide shadows/fog via perf flags.

## 5.1.6 — Single persistent animation loop + loop ownership (no double WebGL context)

- **Purpose:** Establish exactly one RAF render loop for the canonical scene (§5.2 step 8) and eliminate the current two-loops/two-contexts situation, while keeping the loop persistent (§5.1) and mode-aware.
- **Dependencies:** 5.1.1 (canonical scene), 5.1.8 (visibility), 5.1.9 (mode source).
- **Acceptance criteria:** One RAF loop drives the canonical scene; it is started as the last init step (§5.2 step 8); when not in 3D mode it does no GPU work (skips `renderer.render` and per-frame layout/camera updates) but the loop/context **persists** (not torn down); there is never more than one live viewport WebGL context.
- **Implementation notes:** `WordWeaverScene._tick` (WordWeaverScene.js:711–749) already gates `renderer.render` and the heavy `_yearLayout/_timelineViewport/_updateCameraFocus` updates on `getCalendarMode() === "3d"` (734–746) — **keep this pattern**, it's correct. The problems are (a) it auto-starts in the constructor (166) regardless of mode, and (b) `scene.js`'s loop in `main.js` (44–51) runs the *other* context simultaneously. Resolution flows from 5.1.1: if `WordWeaverScene` is canonical, `main.js`'s `animate()` should drive *it* (or the calendar-wall scene is retired), not a second scene. Continue running the RAF even when idle in 2D (cheap — a mode check + early return) so resuming 3D is instant per §5.1 "persists in memory"; the alternative (stop RAF in 2D, restart on 3D) saves the idle check but risks a hitch — document the choice. Source `getCalendarMode()` via the 5.1.9 bus convergence rather than the standalone store if that lands.
- **Edge cases:** Tab hidden (`document.hidden`) — consider pausing RAF to save battery, but ensure resume on `visibilitychange`; mode toggled mid-frame; embedded mode; the satellite day-weave window (if kept, 5.1.1) needs its own loop only while open and disposed on close — that's the *one* legitimate second context, and it must not overlap the year viewport.
- **UI/UX considerations:** Instant 3D resume (persistent loop) supports the seamless 2D↔3D transition (§6.8 / §3 line 77).
- **Data flow notes:** Loop calls `controls.update()` + `renderer.render`; layout/atom updates only in 3D.
- **Testing notes:** In 2D mode, `renderer.info.render.calls` stays flat (no draws) yet the loop is alive; exactly one viewport context across mode toggles; switching to 3D resumes rendering within one frame.
- **Performance notes:** **This is the milestone's key perf fix** — one context instead of two; idle-loop cost is a single comparison per frame.
- **Mobile vs desktop:** Battery — consider `document.hidden` pause on mobile especially.
- **Integration points:** §5.2 (step 8), §5.1, §6.8, §3 line 77, `calendarMode.js`/5.1.9.
- **Status:** **Partial** (render is mode-gated ✓, but RAF auto-starts and a *second* `scene.js` loop/context runs in parallel). **Next:** collapse to one canonical loop/context per 5.1.1; keep the mode-gated render; decide idle-loop vs stop/restart.

## 5.1.7 — Resize handling (window + ResizeObserver, aspect, pixel-ratio re-clamp)

- **Purpose:** Keep the renderer size, camera aspect, and pixel ratio correct across window/container/DPR changes (§5.2 step 9), reconciling the two scenes' resize approaches.
- **Dependencies:** 5.1.1, 5.1.2 (pixel-ratio cap), 5.1.4 (camera aspect).
- **Acceptance criteria:** On resize, `renderer.setSize(w, h)` + `camera.aspect = w/h` + `camera.updateProjectionMatrix()` run; pixel ratio is re-clamped to `min(dpr, 2)` (handles monitor moves); both the window `resize` event and a container `ResizeObserver` are handled (the canonical scene is container-sized, not window-sized, if it sits behind the shell with insets); handler is removed on teardown.
