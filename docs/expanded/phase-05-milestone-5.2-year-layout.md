# Phase 5 — Milestone 5.2: Year Layout (Expanded)

**Goal:** Specify the year-overview construction (`createYearLayout()` — §5.2 step 7, detailed in §5.3): 12 month clusters placed in a ring around the origin, each rotated `(monthIndex / 12) · 2π`, each holding a 7-column `DayBlock3D` grid + a centered month label + a few perimeter `AtomGlyph3D` decorations, with the spec's instance-optimization (`InstancedMesh` for like-materialed day blocks, shared atom geometry, pre-rasterized label textures). This milestone is grounded against the **already-existing** year layout — `WordWeaverYearLayout3D` and its helpers (`createYearLayout` / `populateMonthCluster` / `createMonthLabelMesh`) live inside [`WordWeaverScene.js`](../../src/wordweaver/WordWeaverScene.js):780–1085 — so every task reconciles built / gap / next-step rather than describing greenfield. It does **not** cover the per-day glass panel internals (§5.4 → 5.3) or atom internals (§5.5 → 5.4); those are downstream. It covers how the year is *assembled and arranged*.

**Spec alignment:** §5.3 (Year Layout: ring of 12 month clusters, **radius 80**, rotation `(monthIndex/12)·2π`, clusters face inward / camera outside looking in (line 506); per-cluster: month label centered above, **7×4-or-5** `DayBlock3D` grid, leading/trailing empty cells as **invisible/dimmed blocks** for alignment (line 511), 2–4 perimeter `AtomGlyph3D`; **instance optimization** — like-material day blocks merged into `InstancedMesh`, atoms share one `SphereGeometry`/material, labels use **pre-rasterized canvas textures** not per-frame `TextGeometry`, lines 514–517), §5.2 step 7 (`createYearLayout()` is the 7th init step), §5.4 line 552 (on `eventCreated/Updated/Deleted` the scene identifies **affected** `DayBlock3D`s and queues a canvas re-render **batched to next frame** — i.e. *targeted*, not full rebuild), §16.2 line 1317 (LOD: at year-overview distance, `DayBlock3D` canvas textures are **low-res 128×160**), §16.5 line 1479-1480 (instanced rendering of same-dimension day blocks + automatic frustum culling of off-screen clusters), §2.3 line 157 (both renderers read events **exclusively** through `timelineModel.js`; on mutation each re-renders its **visible portion** via the bus), §13.2 line 1169/1171 (`monthFocused {year, month}` emitted by `WordWeaverScene`; `navigateTo {level}` consumed by it — the focus hooks the year layout must expose).

**Sequencing:** Second milestone of Phase 5; it is literally step 7 of the §5.2 sequence 5.1 just finished plumbing. It depends on 5.1's canonical-scene decision (5.1.1) — the year layout attaches to *that* scene's root — and on 5.1.4's camera params (the ring must be visible from the year-overview vantage; note the **radius/far-plane interaction** 5.1.4 already flagged). It feeds 5.3 (DayBlock3D internals — the grid cells this milestone positions), 5.4 (AtomGlyph3D internals — the decorations this milestone places), 5.5 (camera focus on a month cluster / day block — this milestone exposes the `monthClusters` / `findDayBlock` handles 5.5 animates to), and 5.6 (interaction — raycasting the day blocks this milestone lays out). Carries Phase 5's recurring finding: the layout rebuilds on the **duplicate** `wordweaver/EventBus.js` `timelineUpdated` signal, not the §13.2 catalog (5.1.9), and it does a **full teardown+rebuild** rather than the §5.4 targeted re-render — the central efficiency reconciliation here.

The bones of §5.3 are present. Headline deltas vs §5.3/§16:

- **Ring radius is 26, spec says 80 (`YEAR_RING_RADIUS = 26`, WordWeaverScene.js:783).** At radius 26 the 12 clusters sit on a circumference of ~163 units → ~13.6 units of arc each, but a cluster's day grid is ~10.5 wide (7 cols × `COL_SPACING` 1.5) and up to ~12 tall (6 rows × `ROW_SPACING` 2) — so clusters nearly collide. Radius 80 (circumference ~503, ~42/cluster) gives the breathing room the spec intends. 5.2.1 reconciles, and this couples to 5.1.4 (camera far plane must exceed the ring; far was the latent bug there).
- **Rotation matches spec ✓ (with a start offset):** `angle = (monthIndex/12)·2π − π/2` (WordWeaverScene.js:978) is exactly the §5.3 `(monthIndex/12)·2π` plus a `−π/2` to start January at the "top/front." Keep — just document the offset.
- **Clusters `lookAt(0,0,0)` — they *face inward* (✓ line 506 clause 1) but the camera vantage contradicts clause 2.** `cluster.lookAt(0,0,0)` (WordWeaverScene.js:984) orients each cluster's front toward the origin. §5.3 line 506 says clusters face inward **and** the camera starts **outside** the ring looking in — but a camera outside a ring of inward-facing clusters sees their **backs**. With the current near-center camera (`_cameraHome (0,2.4,8.2)` inside radius 26), you stand *inside* the ring reading the fronts — a coherent "surrounded by months" vantage, but not the spec's outside-in. 5.2.2 must resolve the orientation-vs-vantage contradiction (either flip clusters to face outward for an outside camera, or formally adopt the inside-the-ring overview and update the spec/5.1.4 vantage).
- **Day grid: 7 columns ✓, but rows run to 6 and week-start is hardcoded Monday.** `cellIndex = monOffset + day − 1`, `col = cellIndex % 7`, `row = ⌊cellIndex/7⌋`, `x = (col−3)·COL_SPACING`, `y = −row·ROW_SPACING` (WordWeaverScene.js:917–921) is a correct calendar grid. - **No leading/trailing empty cells (spec line 511 wants invisible/dimmed placeholder blocks).** The loop runs `day = 1..daysInMonth` only (WordWeaverScene.js:902); leading/trailing slots are simply absent. Grid *position* stays aligned (because `cellIndex` includes `monOffset`), but there are no dimmed out-of-month placeholders — the same "dimmed out-of-month days" gap Phase 4.2 flagged for the 2D month grid, now in 3D. 5.2.4.
- **Month label is already a pre-rasterized `CanvasTexture` ✓ (good instinct), but per-month and via `MeshStandardMaterial`.** `createMonthLabelMesh` (WordWeaverScene.js:790–820) draws month name + year onto a 512×128 canvas → `CanvasTexture` on a `PlaneGeometry(3.2, 0.8)` — exactly the §5.3 line 517 "pre-rasterized canvas textures to avoid per-frame `TextGeometry`" intent (the spec even offers `TextGeometry` as an alternative at line 509; the code chose the cheaper path — keep). Gaps: a fresh canvas+texture **per cluster** (12 textures, no atlas/cache), it is **not billboarded** (fixed plane; the `update()` only bobs `position.y`, WordWeaverScene.js:1022–1023, it doesn't face camera), and label disposal isn't in `_clear()` (see 5.2.10). 5.2.5.

Reality: each day is an **individual** `DayBlock3D` (WordWeaverScene.js:924–936) → ~365 day-block object graphs + ~24–48 atoms per full year, all separate draw paths. The code *does* pass `useSharedMaterials: true` (930) — a partial nod (shared materials, the §16.5 "pre-created and shared" half) — but geometry/draw-call instancing is absent. 5.2.7.

This is the milestone's key efficiency reconciliation and dovetails with 5.1.9's bus convergence. 5.2.8.
- **Reads are correctly model-only ✓.** `getEventsForDay(year, monthIndex, day)` and `getInitialNotes()` both come from `timelineModel.js` (WordWeaverScene.js:12–16); the layout holds no event copy — satisfies §2.3 line 157. Keep. (The `Math.random` atoms and `classifyEvent`/`enrichDayEvents` derivation are presentation, not a second source of truth.)
- **Year is hardcoded to the current year; no multi-year navigation.** `const year = new Date().getFullYear()` (WordWeaverScene.js:971); the ring is always *this* calendar year. §5.3 describes "the entire year" without multi-year nav, so this is spec-conformant *today*, but flag it: `navigateTo`/focus across a year boundary has no path. 5.2.10.
- **Week halos are a non-spec embellishment.** Per-week translucent colored planes (`WEEK_HALO_HEX`, WordWeaverScene.js:782, 862–878) are not in §5.3. They're a reasonable depth cue — decide keep-as-enhancement vs trim; either way they must be disposed (they are, in `_clear()` 1049–1053) and counted in the instance budget. 5.2.10.
- **What's already right (keep):** rotation formula ✓, 7-col grid math ✓, month label pre-rasterized ✓, `useSharedMaterials` ✓, atom count 2–4 ✓, model-only reads ✓, `findDayBlock` focus handle ✓, halos/atoms/blocks all disposed in `_clear()` ✓, proximity-based per-block emphasis in `update()` ✓.
