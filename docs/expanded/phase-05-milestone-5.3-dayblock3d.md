# Phase 5 — Milestone 5.3: DayBlock3D (Expanded)

**Goal:** Specify the per-day glass tile (`DayBlock3D` — §5.4): a thin rounded glass panel (`RoundedBoxGeometry 2×2.5×0.15`, `MeshPhysicalMaterial` `transmission 0.7`/`roughness 0.1`/`metalness 0`/`thickness 0.5`) carrying a **single `CanvasTexture` map** of the day's content (day number top-left, AI daily summary ≤2 lines, **up to 3** event rows of icon+time+title, "…+N more", a ⏰ alert badge top-right), a three-state emissive machine (rest 0.25 / hover 0.6 / focus 0.9) with a +0.1 Y hover translation, a **queued, batched** canvas re-render (≤3 textures/frame), LOD texture tiers (128×160 overview / 256×320 month / 512×640 focus), and `InstancedMesh` panel support. This milestone is grounded against the **already-existing** [`DayBlock3D.js`](../../src/wordweaver/DayBlock3D.js) — so every task reconciles built / gap / next-step, not greenfield. It owns the per-day tile internals that 5.2 *positioned*; it does **not** cover ring assembly (5.2), atom internals (§5.5 → 5.4), camera focus animation (§5.6 → 5.5), or raycast/hover wiring (§5.7 → 5.6) — it exposes the hooks those consume.

**Spec alignment:** §5.4 (geometry `BoxGeometry(2,2.5,0.15)` + `RoundedBoxGeometry` corners, line 523-525; `MeshPhysicalMaterial` `transmission 0.7`/`roughness 0.1`/`metalness 0`/`thickness 0.5`, **no crack/fracture shaders**, line 528-530; `emissive` = dominant category color, `emissiveIntensity` 0.25/0.6/0.9 rest/hover/focus, line 531-532; **single `CanvasTexture` map overlay** updated on data change, line 534-535; canvas content = day number top-left grey, AI summary ≤2 lines white, **≤3** event rows icon+time+title, "…+N more", ⏰ top-right if any alert, line 537-542; resolution **256×320 (2× retina 512×640)**, line 544; state transitions incl. **+0.1 Y** on hover @150ms and focus camera-pan + day-detail panel, line 546-549; **content update** on `eventCreated/Updated/Deleted` → identify affected blocks, **queue canvas re-render batched to next frame**, line 551-552), §4.x line 427 (`generateDailySummary(date)` → 2–3 sentence NL summary used in DayBlock3D content), §16.1 line 1306-1307 (frame loop **processes the re-render queue, max 3 textures/frame**), §16.2 line 1311-1313 (the queue exists precisely to avoid bulk-update frame drops), §16.3 line 1317-1319 (LOD: 128×160 overview / 256×320 month / 512×640 focus, by camera distance), §16.5 line 1479 (same-dimension `DayBlock3D` panels share one `InstancedMesh`, category materials pre-created/shared), §22 line 1912 ("today" = a visually distinct `DayBlock3D` variant / glowing anchor), §20.x line 1632 (icons rasterized from the same SVG source at 16×16 into the canvas), §23 line 1653-1654 (hover 150ms ease-out / unhover 200ms ease-in), §5.7 line 610 (hover tooltip = day number + event count + dominant category).

**Sequencing:** Third milestone of Phase 5. It depends on 5.1's canonical scene/material conventions and 5.2's layout (5.2 places the blocks this milestone builds; 5.2.7's *scene-level* instancing is realized here via this milestone's *block-level* `InstancedMesh` panel support, resolving the per-day-content-vs-instancing tension 5.2.7 flagged as "decide with 5.3"; 5.2.8's *targeted re-render* feeds this milestone's *per-block* queued canvas update; 5.2.4's dimmed placeholders consume the empty/dimmed block variant defined here; 5.2.9's LOD tiers consume the texture-resolution tiers defined here). It feeds 5.4 (atom internals share the same shared-resource discipline), 5.5 (camera `focusOnDay` frames the block + reads its world position/today-anchor), and 5.6 (raycaster tests these panels, drives the hover/focus emissive states and the tooltip data this milestone exposes). It carries Phase 5's recurring findings: the **duplicate `wordweaver/EventBus.js`** drives an immediate full-label rebuild rather than the §13.2-bus queued re-render (5.1.9 / 5.2.8), and the per-day content path is the central efficiency reconciliation.

## Current implementation status (reconciliation)

`DayBlock3D` **already exists and is substantially built** ([`DayBlock3D.js`](../../src/wordweaver/DayBlock3D.js):196–430) — this is an upgrade/reconcile milestone. But it took a **fundamentally different rendering approach** than §5.4 in two big ways: it is a **flat plane**, not a thin glass box, and it renders content as **per-line billboarded `THREE.Sprite`s** (each with its own small `CanvasTexture`), not a **single `CanvasTexture` map** on the panel. The state model is also a **2-state camera-proximity** scheme, not the §5.4 3-state rest/hover/focus machine. The shared-resource scaffolding and an (unused) `InstancedMesh` panel class are present. Headline deltas vs §5.4/§16:

- **Geometry: flat `PlaneGeometry(1.2, 1.6)`, spec wants `RoundedBoxGeometry(2, 2.5, 0.15)`.** The panel is `new THREE.PlaneGeometry(PLANE_W=1.2, PLANE_H=1.6)` (DayBlock3D.js:5-6, 28, 242) — a **flat, zero-thickness** quad at the **wrong dimensions** (spec is 2×2.5, ~1.25× larger and a different aspect). There is **no thickness** (§5.4 wants 0.15 depth) and **no rounded corners** (`RoundedBoxGeometry` from `three/examples/jsm/geometries/`). The "glass box" is faked with three stacked planes: the panel, a `noteSurface` quad (`1.1×1.4`, z+0.006), and a backside `eventGlow` edge quad (`1.03×`, z−0.006). 5.3.1 reconciles to the rounded box. (Note: dimensions ripple into 5.2's `COL_SPACING`/`ROW_SPACING` footprint — coordinate with 5.2.1.)
- **Material: clearcoat fake-glass, no `transmission`/`thickness`, emissive lives on a *separate* halo mesh.** The panel `MeshPhysicalMaterial` (DayBlock3D.js:31-40) is `color #0a0a0a`, `opacity 0.92`, `roughness 0.15`, `metalness 0.05`, `clearcoat 1.0`, `clearcoatRoughness 0.1` — a dark glossy panel, **not** the spec's transmissive glass (`transmission 0.7`, `roughness 0.1`, `metalness 0`, `thickness 0.5`, line 528). The panel itself is **not emissive**; instead a backside `eventGlow` `MeshStandardMaterial` (264-272, `emissive` = category color, `emissiveIntensity 0.25`, `BackSide`, `opacity 0.35`) supplies the colored halo. §5.4 line 531 wants the **panel's** `emissive` set to the category color. The "no cracked/fracture shaders" rule (line 530) is satisfied (a `updateSharedCrackTime` no-op confirms crack shaders were removed, DayBlock3D.js:51-52 — keep). 5.3.2 reconciles material; 5.3.5 reconciles emissive states. Decide whether to keep the separate halo as an *enhancement* or move emissive onto the panel per spec.
- **Content: per-line `Sprite`s with individual `CanvasTexture`s, not one panel `CanvasTexture` map — the headline divergence.** §5.4 line 534-535 is explicit: a **single** `CanvasTexture` used as the panel's `map`, redrawn on data change. The code instead builds a **billboarded `THREE.Sprite` per line** — `createEventSprite` (DayBlock3D.js:131-146) and `createSummarySprite` (152-165) each call `createLabelTexture` (105-123) to make their **own** small canvas (256×64 / 280×56 / 300×48) → `CanvasTexture` → `SpriteMaterial` → `Sprite`. So a populated day is ~6–7 sprites, each a separate texture + draw, all camera-facing (quaternion-copied in `update`, 402-407). This **multiplies texture count** (~6/day × 365 ≈ thousands of small textures) and **defeats instancing** (5.3.7). 5.3.3 reconciles to the single-canvas model.
- **Summary is a count-string, not the AI daily summary.** `buildDaySummary` (DayBlock3D.js:170-178) returns `"{count} · {DominantCategoryLabel}"` (e.g. "3 · Work") — **not** the §5.4 line 539 / §4 line 427 "AI daily summary sentence (2–3 sentences, NL)" from `generateDailySummary(date)`. 5.3.3 wires the real summary (truncated to 2 lines).
- **Event-row count is 5, spec says 3; no "+N more"; alert is inline not a corner badge.** `MAX_SURFACE_LINES = 5` (DayBlock3D.js:10, sliced at 347) — spec line 540-541 caps visible rows at **3** with a "…+N more" indicator for the remainder (**absent** here). The ⏰ alert is applied **inline per event** (`_normalizeEvents`, 307-308: alarm/reminder/`alertId` → icon becomes ⏰), but §5.4 line 542 wants a **single ⏰ badge in the top-right corner** if *any* alert exists that day. Day number is a 📅 sprite (282-287), not the spec's "top-left small grey **number**". 5.3.4 reconciles rows + "+N more" + corner alert + day-number placement.
- **State model: 2-state camera-proximity, not 3-state rest/hover/focus.** `setProximity(near)` (DayBlock3D.js:378-385) is a **binary** driven by *camera distance* in the scene (`dist < 4.2 || isFocused`, WordWeaverScene.js:1032) — it sets target scale 1.08, glow 0.42, sprite opacity. §5.4 line 546-549 wants **three discrete** emissive levels (rest 0.25 / **hover** 0.6 / **focus** 0.9), a **+0.1 Y translation on hover**, 150ms-ease-out hover / 200ms-ease-in unhover (§23 line 1653-1654), with **hover driven by the raycaster** (5.6), not proximity. The emissive also currently animates on `eventGlow`, not the panel (5.3.2). 5.3.5 introduces the real machine (proximity can remain as an LOD/ambient cue, but hover/focus are raycast-driven).
- **`setEvents()` re-renders immediately; no queue, no batch, no ≤3/frame cap.** `setEvents` (DayBlock3D.js:366-373) calls `_rebuildSurfaceLabels()` **synchronously** — disposing and recreating all sprite textures inline. §5.4 line 552 + §16.1 line 1306-1307 + §16.2 line 1311-1313 want the scene to **queue** affected blocks and the **frame loop** to flush **≤3 canvas re-renders/frame**. No such queue exists (and the scene does a full rebuild anyway — 5.2.8). 5.3.6 introduces the per-block dirty/queue API consumed by the frame loop.
- **`InstancedMesh` panel class exists but is DEAD.** `DayBlockInstancedPanels` (DayBlock3D.js:57-97) is a complete instanced-panel helper (shared `panelGeo`/`panelMat`, `instanceColor`, `DynamicDrawUsage`, `finalize()`) — but **nothing constructs it**; the scene builds **individual** `new DayBlock3D` per day (WordWeaverScene.js:924). So §16.5 line 1479 instancing is *scaffolded but unused*, and the per-instance **content** problem (one InstancedMesh = one shared map, but each day needs its own canvas) is unsolved. This is the 5.2.7 "decide with 5.3" tension. 5.3.7 resolves it (instance the glass panel; carry per-day content via atlas/overlay).
- **Resolution is fixed; no retina 2×, no LOD tiers.** `createLabelTexture` uses fixed canvas sizes regardless of `devicePixelRatio` (§5.4 line 544 wants 256×320 base / **512×640 retina**), and there is **no LOD tier** (§16.3: 128×160 overview / 256×320 month / 512×640 focus). The scene computes per-block camera distance already (WordWeaverScene.js:1030) — the signal exists; the tiers don't. 5.3.8.
- **Today marker is faint; pick/tooltip data is thin.** `isToday` only bumps `eventGlow.emissiveIntensity` to 0.38 (DayBlock3D.js:291-293) — §22 line 1912 wants a **visually distinct today variant / anchor**. For picking, the group carries `userData.dayBlock = this` (224) and `name = day-block-${dateIso}` (223-224) — a good handle for 5.6 — but no exposed `{ dayNumber, eventCount, dominantCategory }` for the §5.7 line 610 hover tooltip. 5.3.9.
- **What's already right (keep):** `MeshPhysicalMaterial` chosen for the panel ✓ (just needs the glass params), **no crack/fracture shaders** ✓ (line 530, `updateSharedCrackTime` no-op), shared-resource path (`getSharedDayBlockResources`, `useSharedMaterials`) ✓, `classifyEvent`-derived icon/color/category/priority normalization ✓, model-only inputs (events passed in, no second source) ✓, billboarding math (`quaternion.copy(camera.quaternion)`) ✓ for whatever stays sprite-based, smooth `lerp` toward target scale/glow ✓, sprite/edge/label **disposal** present ✓ (411-429), `userData.dayBlock` + stable `name` pick handle ✓, `DayBlockInstancedPanels` scaffold ✓ (just wire it).
