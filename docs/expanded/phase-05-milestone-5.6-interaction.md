# Phase 5 — Milestone 5.6: Interaction Model (3D) (Expanded)

**Goal:** Specify the WordWeaver 3D interaction layer (§5.7): a `Raycaster` driven from the pointer that tests **`DayBlock3D` meshes (and month labels)**, acting on the **first intersection** — producing **hover** (block emissive increase + Y translation, pointer cursor, a tooltip showing day number + event count), **click/tap** (focus the block via `focusOnDay`; a second click on an already-focused day **opens the day detail panel**), **month-label click** (`focusOnMonth`), **non-interactive empty/decorative surfaces** (padding days and `AtomGlyph3D` atoms are ignored), and **keyboard navigation** (arrows move focus between adjacent blocks, Enter focuses, Escape steps month-overview → year-overview). This milestone is grounded against the **already-existing** pick path inside [`WordWeaverScene.js`](../../src/wordweaver/WordWeaverScene.js) (`_raycaster`/`_pointer`, `_pointerToNdc`, `_collectClickTargets`, `_pick`, `_handlePointerMove`, `_handlePointerDown`, the `pointermove`/`pointerdown` listeners) and the [`DayBlock3D.js`](../../src/wordweaver/DayBlock3D.js) state hooks (`setProximity`, `userData.dayBlock`, `group.name`) — so every task reconciles built / gap / next-step, not greenfield. It owns the **pick → hover/click → focus/panel routing**; it consumes 5.4.8 (atom raycast-exclusion contract), 5.5.8 (the day-panel trigger rule), and 5.5.9 (the §13.2 bus emit/consume); it does **not** own the camera move itself (5.5), the day tile visuals (5.3), the ring layout (5.2), or the decorations (5.4).

**Spec alignment:** §5.7 line 604-624 (Raycaster updated **each animation frame**, tests **all `DayBlock3D` meshes**, only the **first** intersection acted upon, lines 606-607; hover = emissive increase + Y translation, pointer cursor, **tooltip day-number + event-count near cursor**, lines 609-610; click/tap → focused `DayBlock3D` triggers `focusOnDay()`, **second click on an already-focused day opens the day detail panel**, lines 612-613; **month-label click → `focusOnMonth()`**, lines 615-616; **empty/out-of-month day blocks non-interactive**, invisible/near-transparent, **raycaster ignores them**, lines 618-619; **keyboard nav** — arrows move focus between adjacent blocks, Enter focuses the keyboard-focused day, **Escape returns camera month-overview → year-overview**, lines 621-624), §16.1 line 1304 (frame-loop step 3 = "Raycast from camera through pointer; update hover state"), §13.2 line 1418 (3D navigation updates `focusedDate`, emits `dayFocused`/`monthFocused`), §13.2 line 1101-1102 (pick exemplar: click day → `focusOnDay(3,14)` → camera lerps), §5.5 line 562 (atoms have **no interactive function** — the 5.4.8 exclusion this milestone enforces in the raycaster), §1.4 line 88 (interaction must stay responsive — raycast can't blow the frame budget), §27 (mobile touch ergonomics — tap vs orbit-drag).

**Sequencing:** **Sixth and final milestone of Phase 5.** It depends on 5.1 (the canonical scene that owns the pointer listeners and the per-frame loop), 5.2 (the layout supplies `dayBlocks`/`monthClusters`/`findDayBlock` and the grid adjacency keyboard nav walks), 5.3 (the `DayBlock3D` hover/focus state hooks — and the 5.3.5 finding that the block has only a **binary camera-proximity** state, not a 3-state rest/hover/focus, which this milestone's raycast-hover completes), 5.4.8 (the atom non-interactive contract this raycaster honors), and 5.5 (the focus API + day-panel rule + bus wiring this routing **calls into** — 5.6 turns a pick into a 5.5 `focusOn*` call). It carries the two Phase-5 recurring threads: the **duplicate / parallel-stack** pattern — here **two pick systems** coexist (`_collectClickTargets` mixes the **year-ring `DayBlock3D`** meshes **and** the satellite-timeline `_pickables` nodes, WordWeaverScene.js:645-657) — and the **§13.2 event-bus gap** (clicks route through a constructor `onNodeClick` callback, not the Phase-2 bus — 5.6.10, consuming 5.5.9).

## Current implementation status (reconciliation)

A working pick path **already exists and is live in the year ring** — a `Raycaster`, pointer→NDC conversion, a target collector, a parent-walk to resolve the hit `DayBlock3D`, a hover cursor, and a click that calls `focusOnDay`. But it is **event-driven, not per-frame**; hover sets **only the cursor** (no block emissive/Y state, no tooltip); click **immediately** focuses **and** fires a callback with a **fabricated note** (no second-click-opens-panel two-step); **month labels aren't pickable** (so `focusOnMonth` is never reached from interaction); there's **no tap-vs-orbit-drag discrimination** (orbiting from a block focuses unintentionally); there's **no keyboard navigation**; the target list is **rebuilt every pointer event** over ~365×3 meshes (perf); it routes through a constructor **callback, not the §13.2 bus**; and it mixes **two pick systems**. This is an upgrade/reconcile + complete milestone, not greenfield.

- **Two pick systems mixed in one collector.** `_collectClickTargets` (WordWeaverScene.js:645-657) gathers **both** the satellite-timeline `_pickables` node meshes (traversed) **and** every year-ring `DayBlock3D`'s `panel`/`noteSurface`/`eventGlow` — and `_pick` (:659-672) resolves either a `userData.dayBlock` **or** a `userData.node`. In **3D year mode** the spec (§5.7 line 607) wants the raycaster to test **`DayBlock3D` meshes** (and labels, line 615); the timeline-node pick is a *different* subsystem (the satellite weave window). 5.6.1 scopes the year-ring pick to day blocks + month labels and reconciles/segregates the timeline-node path.
- **Raycast is event-driven (pointermove/pointerdown), not per-frame.** §5.7 line 607 / §16.1 line 1304 describe a raycaster **updated each animation frame** (frame-loop step 3). Live binds `pointermove → _handlePointerMove` and `pointerdown → _handlePointerDown` (WordWeaverScene.js:137-138) and raycasts **inside those events** — there is **no** per-frame raycast in `_tick` (WordWeaverScene.js:711-732). Event-driven is arguably *cheaper* (no idle raycasts) and is a legitimate design — but it diverges from the spec's per-frame model and means hover doesn't update when the **camera** moves under a stationary pointer (e.g. during a focus lerp or fly). 5.6.2 reconciles cadence (keep event-driven + a camera-moved re-pick, or move to throttled per-frame) and **caches the target list**.
- **The target list is rebuilt on every pointer event over hundreds of meshes.** `_collectClickTargets` (WordWeaverScene.js:645-657) allocates a fresh array and **traverses** every `_pickables` group plus pushes 3 meshes per day block (~365 days × 3 ≈ 1,100 meshes) **on every `pointermove`** (which fires continuously). That is a per-move allocation + traversal + a full `intersectObjects` over ~1,100 objects — the §1.4 line 88 / §16 responsiveness risk. 5.6.2 caches a flattened pickable array (rebuilt only on layout change) and considers bounding-volume/`Layers` narrowing.
- **Hover sets only the cursor — no block hover state, no tooltip.** §5.7 line 609-610 wants the intersected block to enter a **hover state (emissive increase + Y translation)**, the cursor to become a pointer, **and a tooltip** (day number + event count) near the cursor. Live `_handlePointerMove` (WordWeaverScene.js:674-682) only tracks `_hovered` (a dateIso string) and toggles `canvas.style.cursor` between `"pointer"`/`"grab"` — it does **not** call any hover method on the `DayBlock3D` and shows **no tooltip**. The block's only state hook is `setProximity(near)` (DayBlock3D.js:378-385), which is **camera-distance-driven** (set in `layout.update` at `dist < 4.2`, WordWeaverScene.js:1031-1032), **not** raycast-hover — the 5.3.5 finding (binary proximity, not 3-state rest/hover/focus). 5.6.3 adds a raycast-driven hover state distinct from proximity; 5.6.4 adds the tooltip.
- **Click immediately focuses *and* fires a fabricated callback — no second-click-opens-panel two-step.** §5.7 line 612-613: a click triggers `focusOnDay()`, and **if the day is already focused, a second click opens the day detail panel**. Live `_handlePointerDown` (WordWeaverScene.js:684-698) calls `focusOnDay(...)` **and** immediately `onNodeClick({date, time:"12:00", text:"Day N", node})` with a **fabricated note** (`time:"12:00"`, `text:"Day {day}"`) on the **first** interaction — there is no "already-focused → open panel" gate, and the fake note is a code smell (it invents data the model doesn't have). It also fires on **`pointerdown`** (not a click/tap-up), so it can't distinguish a tap from the start of an orbit drag (5.6.6). 5.6.5 implements the focus-then-second-click-panel rule (reconciled with 5.5.8) and removes the fabricated note.
- **No tap-vs-orbit-drag discrimination.** Because the action fires on `pointerdown` (WordWeaverScene.js:684), **any** press that lands on a block focuses it — including the press that *begins an OrbitControls drag* to orbit the scene. The user can't rotate the view starting from a day block without triggering a focus. §5.7 line 612 ("on click/tap") and §27 (touch) imply a true click/tap (down→up with little movement). 5.6.6 adds a movement-threshold + down/up pairing so dragging orbits and only a stationary tap focuses.
- **Month labels aren't pickable — `focusOnMonth` is never reached from interaction.** §5.7 line 615-616: clicking a **month label** triggers `focusOnMonth()`. Live month labels (`createMonthLabelMesh` → `label.mesh`, WordWeaverScene.js:898-900) are added to the cluster but carry **no pick `userData`** and are **not** included in `_collectClickTargets` (which only gathers `_pickables` + day-block meshes) — so a label click hits nothing, and `focusOnMonth` (WordWeaverScene.js:214, which *exists*) is **never** invoked by the pointer. 5.6.7 makes labels pickable and routes them to `focusOnMonth`.
- **Empty/out-of-month days: the 3D ring currently has none — but 5.2.4 may add them, and they must stay non-interactive.** §5.7 line 618-619 says empty/out-of-month day blocks are non-interactive and the raycaster ignores them. Live `populateMonthCluster` creates `DayBlock3D` **only** for `day = 1..daysInMonth` (WordWeaverScene.js:902-936) — there are **no leading/trailing padding blocks** (the 5.2.4 finding: "NO leading/trailing dimmed empty cells per line 511"). So today there's nothing to ignore — but **if 5.2.4 adds dimmed padding cells**, they must be excluded from the pick set (and `AtomGlyph3D` atoms must be excluded per 5.4.8). 5.6.8 makes the non-interactive contract explicit for both.
- **No keyboard navigation (arrows / Enter / Escape).** §5.7 line 621-624 wants arrow keys to move focus between adjacent day blocks, Enter to focus the keyboard-focused day, and **Escape to step camera month-overview → year-overview**. The only keyboard handling in 3D is the **fly movement** (WASD/Q-E, 5.5.6) in `WordWeaverTimelineViewport`/`WordWeaverChrome` — there is **no** day-focus keyboard nav and **no** Escape-to-overview. 5.6.9 adds grid-adjacency arrow nav + Enter; Escape's camera half is coordinated with 5.5.10.
- **Routes through a constructor `onNodeClick` callback, not the §13.2 bus.** Clicks call `this.onNodeClick({...})` (WordWeaverScene.js:691-708) — a constructor-injected callback — **not** the Phase-2 `src/utils/EventBus.js`. So a pick emits **no** `dayFocused`/`monthFocused` and opening the day panel is wired through the callback chain, not the §13.2 contract (the recurring Phase-4/5 bus gap, and the 5.5.9 wiring this should consume). 5.6.10 routes interaction through the canonical bus.
- **What's already right (keep):** a single `Raycaster` + reused `_pointer` `Vector2` (no per-event allocation of those) ✓ (WordWeaverScene.js:114-115); correct **pointer→NDC** math accounting for canvas rect (`_pointerToNdc`, :639-642) ✓; **first-intersection** semantics (`hits[0]`, :664) ✓ (§5.7 line 607); robust **parent-walk** to resolve the owning `DayBlock3D` via `userData.dayBlock` (:664-669) — works regardless of which child mesh is hit ✓; stable pick handle (`group.name = "day-block-{iso}"` + `userData.dayBlock`, DayBlock3D.js:224-225) ✓; **Pointer Events** (unified mouse+touch) ✓; `preventDefault`/`stopPropagation` on a real hit so the canvas doesn't also pan ✓ (:688-689); pointer listeners are **removed on dispose** (WordWeaverScene.js:761-762) ✓; hover **cursor** feedback exists ✓ (:680); atoms are **already not** in the pick set (added to clusters but not `_pickables`/`dayBlocks`) — so 5.4.8 is currently satisfied *implicitly* (5.6.8 makes it explicit) ✓.

## 5.6.2 — Raycast cadence (per-frame vs event) & cached pickable targets

- **Purpose:** Reconcile the raycast cadence to §5.7 line 607 / §16.1 line 1304 (raycaster "updated each animation frame", frame-loop step 3) versus the live **event-driven** raycast, and eliminate the **per-event rebuild** of a ~1,100-mesh target list — so hover stays correct when the camera moves and the pick cost stays within the §1.4 frame budget.
- **Dependencies:** 5.6.1 (the scoped target set to cache), 5.6.3 (hover consumes the result), 5.1 (the frame loop / `_tick`), 5.5.4 (camera moves that should re-pick); §5.7 line 607, §16.1 line 1304, §1.4 line 88.
- **Acceptance criteria:** The pickable target array is **cached** (built once per layout change — when `dayBlocks`/labels are (re)created in 5.2's build/rebuild — not per pointer event); the raycast either (a) runs **per-frame** in `_tick` against the cached set (spec-literal, frame-loop step 3) **or** (b) stays **event-driven on pointermove** *plus* re-picks when the **camera moves** under a stationary pointer (so a focus lerp/fly updates hover) — pick one and document; hover updates correctly while the camera animates; no per-event array allocation/traversal of the full block set remains; the per-frame/per-move raycast cost is bounded (measured within budget at full ring).
- **Implementation notes:** Replace the per-call `_collectClickTargets` allocation (WordWeaverScene.js:645-657) with a cached `this._pickTargets` rebuilt in the layout build/rebuild path (5.2.8) and invalidated on rebuild; if going per-frame, move the `setFromCamera`+`intersectObjects` into `_tick` (gated to `getCalendarMode()==="3d"`, WordWeaverScene.js:729) using the last known `_pointer`; if staying event-driven, add a re-pick when `_cameraFocus`/fly changed the camera since last pointer move. Consider `Layers` (put interactive day blocks on a dedicated layer and set `raycaster.layers`) or per-cluster bounding-sphere pre-cull to shrink the test set further.
- **Edge cases:** A per-frame raycast every frame even when idle is wasted work — throttle to "pointer or camera changed since last frame"; the cached target set must invalidate on layout rebuild (5.2.8 full rebuild) or stale meshes get tested; pointer leaving the canvas must clear hover (no listener fires inside, so add a `pointerleave` clear, ties to 5.6.3); during a focus lerp the hovered block under the cursor changes — the camera-moved re-pick covers it.
- **UI/UX considerations:** Hover that lags or sticks (stale during camera motion) feels broken; the cached/throttled approach keeps it crisp without burning frames.
- **Data flow notes:** Layout build → cached targets; pointer/camera change → raycast → hover/click resolution.
- **Testing notes:** Target array is built once per layout (instrument the builder), not per pointer event; hover updates while the camera animates over a still pointer; `renderer`/profiler shows no per-move allocation spike; idle frames do no raycast.
- **Performance notes:** This is the headline interaction-perf fix — removes ~1,100-mesh allocation+traversal per `pointermove` and bounds the raycast via caching/layers (§1.4 line 88).
- **Mobile vs desktop:** Mobile has no hover (5.6.3) — the per-move raycast there is only for tap resolution; desktop benefits most from caching during continuous hover.
- **Integration points:** §5.7 line 607, §16.1 line 1304, 5.6.1 (set), 5.6.3 (hover), 5.2.8 (rebuild invalidation), 5.1 (`_tick`).
- **Status:** **Divergent (cadence) + costly (rebuild).** Raycast is event-driven (not per-frame) and rebuilds a ~1,100-mesh target list every `pointermove`. **Next:** cache the target set (invalidate on rebuild), choose per-frame or event+camera-moved re-pick, narrow via layers/bounds.

## 5.6.3 — Raycast-driven hover state on `DayBlock3D` (emissive + Y translation)

- **Implementation notes:** Add a `setHover(on)` to `DayBlock3D` (alongside `setProximity`, DayBlock3D.js:378-385) that adjusts `edgeMat.emissiveIntensity` and a target +Y offset, eased in the block's `update` (the existing lerp at DayBlock3D.js:392-399 is the pattern); in `_handlePointerMove`/the per-frame pick (5.6.2), when `_hovered` changes, call `setHover(false)` on the old block and `setHover(true)` on the new (resolve the block from `userData.dayBlock`, not just the dateIso string the live code stores). Keep the cursor toggle (WordWeaverScene.js:680). Add a `pointerleave` handler to clear hover (5.6.2 edge case).

- **UI/UX considerations:** A subtle emissive+lift makes the hovered day feel responsive and "pickable" before the click — the core affordance the cursor alone (live) doesn't convey; eased, not snapped, keeps it calm (§1.4).
- **Data flow notes:** Raycast hit (5.6.2) → `_hovered` block → `setHover` → eased visual in `update`.
- **Testing notes:** Hovering a day raises its emissive + lifts it slightly; moving off restores it; only one block hovered at once; hover and proximity/focus compose per the precedence; reduced motion drops the lift.
- **Performance notes:** One `setHover` toggle per hover change (not per frame) — negligible; the eased update is already in the block's per-frame `update`.
- **Mobile vs desktop:** Desktop only (touch has no hover); mobile gets tap feedback via 5.6.5, not hover.
- **Integration points:** §5.7 line 609, §16.1 line 1304, 5.3.5 (3-state model), 5.6.2 (hit source), 5.6.4 (tooltip pairs with hover), 5.6.10 (reduced-motion).

## 5.6.5 — Click/tap → `focusOnDay`; second click on focused day → open day panel

- **Purpose:** Reconcile the click/tap behavior to §5.7 line 612-613 — a click/tap focuses the day via `focusOnDay()`, and a **second** click on the **already-focused** day **opens the day detail panel** — replacing the live single-`pointerdown` path that **immediately** focuses **and** fires `onNodeClick` with a **fabricated note**, and aligning with the day-panel-trigger rule settled in 5.5.8.

## 5.6.6 — Tap vs orbit-drag discrimination (down/up + movement threshold)

- **Purpose:** Distinguish a **tap/click** (focus intent) from the **start of an orbit/pan drag** (camera intent), so a user can rotate the scene starting on a day block without triggering `focusOnDay` — fixing the live behavior where the action fires on raw `pointerdown` (WordWeaverScene.js:684) and any press on a block focuses it.
- **Dependencies:** 5.6.5 (the click action being gated), 5.5.5/5.5.7 (OrbitControls/touch own the drag), 5.6.2 (the pick at down/up); §5.7 line 612 ("on click/tap"), §27 (touch drag).
- **Acceptance criteria:** The focus/panel action fires only when `pointerdown` and `pointerup` land on the **same** block with **little movement** between them (below a small px threshold) within a short time — i.e. a genuine click/tap; a press-and-drag (movement beyond the threshold) is treated as an **orbit/pan** and triggers **no** focus; this works for both **mouse** and **touch** (Pointer Events); it doesn't break OrbitControls' own drag handling (the canvas still orbits/pans); `preventDefault`/`stopPropagation` is applied only when committing a tap on a real hit (not on drags, so OrbitControls still gets the drag).
- **Implementation notes:** Replace the immediate-action `_handlePointerDown` with a down/up pair: on `pointerdown` record the pointer position, the pick, and time (don't act); on `pointerup` (or `pointermove` exceeding the threshold → cancel), if movement < threshold (e.g. ~5px) and same block, fire the 5.6.5 action; otherwise treat as a drag and do nothing. Be careful **not** to `preventDefault` on the down (that would block OrbitControls' drag) — only consume the event when committing a tap. Add `pointercancel` handling (touch interruptions).
- **Edge cases:** A tiny jitter during a tap (especially touch) must stay under the threshold — tune for touch (slightly larger threshold); a drag that starts on a block but releases over another block = orbit, not focus; multi-touch (pinch-zoom, 5.5.7) must never register as a tap; releasing outside the canvas = cancel; the threshold in px should account for devicePixelRatio.
- **UI/UX considerations:** Being able to orbit from anywhere — including over a day — is essential for a free-look 3D space; the current "any press focuses" makes the scene feel like it grabs you.
- **Data flow notes:** down (record) → move (maybe cancel) → up (commit if tap) → 5.6.5 action.
- **Testing notes:** Click-without-moving focuses; press-drag from a block orbits and does **not** focus; touch tap focuses, touch drag orbits; pinch never focuses; release-outside cancels; OrbitControls drag still works from over a block.
- **Performance notes:** Negligible (a couple of stored coords); removes spurious focus calls during orbiting.
- **Mobile vs desktop:** Both; touch uses a slightly larger movement threshold.
- **Integration points:** §5.7 line 612, §27, 5.6.5 (gated action), 5.5.5/5.5.7 (drag owners), 5.6.2 (pick).
- **Status:** **Missing.** Action fires on raw `pointerdown` — any press on a block focuses, so orbiting from a day is impossible. **Next:** down/up + movement-threshold tap discrimination (mouse+touch), don't `preventDefault` drags, handle `pointercancel`.
