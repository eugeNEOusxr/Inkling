# Phase 5 — Milestone 5.5: Camera System (Expanded)

**Goal:** Specify the WordWeaver 3D camera (§5.6): a `PerspectiveCamera` (FOV 60°, near 0.1, far 2000, aspect on resize) driven by `OrbitControls` on desktop and a **custom touch handler** on mobile, with three canonical poses (year overview `(0, 60, 120)` → origin; month focus ~20 units out; day focus close-framed on a `DayBlock3D`), **lerp-based transitions** (`camera.position.lerpTo(target, 0.08)` + `controls.target.lerpTo(lookAt, 0.08)` per frame, snap when distance < 0.01), and a focus API — `focusOnDay`, `focusOnMonth`, `focusOnToday`, `focusOnNextEvent`, `focusOnCategory`. This milestone is grounded against the **already-existing** inline camera logic inside [`WordWeaverScene.js`](../../src/wordweaver/WordWeaverScene.js) (`_frameYearCamera`, `focusOnMonth`, `focusOnDay`, `_startCameraFocus`, `_updateCameraFocus`), the **standalone** [`CameraController.js`](../../src/calendar/CameraController.js) used by the 2D-wall `CalendarApp`, the desktop fly-input in [`WordWeaverTimelineViewport.js`](../../src/wordweaver/WordWeaverTimelineViewport.js) and [`WordWeaverChrome.js`](../../src/wordweaver/WordWeaverChrome.js), and the mobile overlay [`WordWeaverMobileControls.js`](../../src/wordweaver/WordWeaverMobileControls.js) — so every task reconciles built / gap / next-step, not greenfield. It owns the camera **intrinsics, poses, transitions, controls, and focus API**; it does **not** cover the raycaster / hover / click routing (§5.7 → 5.6), the day tile (5.3), the ring/cluster layout that *supplies* world positions (5.2), or decorations (5.4 — which must stay world-fixed as the camera moves, 5.4.5's contract).

**Spec alignment:** §5.6 line 565-602 (camera type `PerspectiveCamera` FOV 60° near 0.1 far 2000 line 567; `OrbitControls` desktop with left-drag orbit / right-drag pan / wheel zoom / **WASD fly** / **Q-E elevate-descend** / **R reset** lines 569-575; custom touch handler mobile — single-drag orbit, pinch zoom, two-finger pan, thumb-slide fly, fly/descend buttons lines 577-583; poses year `(0,60,120)`→origin, month ~20 out, day close-framed lines 585-588; transitions `lerpTo(...,0.08)` per frame + snap < 0.01 lines 590-595; focus API `focusOnDay`/`focusOnMonth`/`focusOnToday`/`focusOnNextEvent`/`focusOnCategory` lines 597-602), §5.6 line 487 ("Create `PerspectiveCamera` (FOV 60, near 0.1, far 1000)" — the scene-init restatement; note the **far-plane disagreement** 1000 vs 2000, both > the live 80, ties to 5.1.4), §11 line 147 (Camera = `PerspectiveCamera` + `OrbitControls` desktop + custom touch mobile), §11 line 1011 (the architecture tree lists `CameraController` under the scene), §16.1 line 1302 (frame-loop step 1 = "Update `OrbitControls` (desktop) or custom touch controls"), §13.2 line 1418 ("User navigates in 3D → updates `focusedDate`, emits `dayFocused`/`monthFocused` → camera animates"), §13.2 line 436 (both `WordWeaverScene` and `Calendar2D` should listen `navigateTo`), §13.2 line 1101-1102 / 1278 (`focusOnDay(3,14)` / `focusOnMonth(5)` data-flow exemplars), §23.2 line 1655 ("Camera navigate | focusOnDay/Month | continuous | lerp factor 0.08"), §23.3 line 1664 (under `prefers-reduced-motion`, **camera transitions snap immediately** — lerp factor set to 1 for one frame), §5.7 line 624 (Escape returns camera month-overview → year-overview — interaction-side, coordinated with 5.6), §1.4 line 88 (motion never costs readability/perf).

**Sequencing:** Fifth milestone of Phase 5. It depends on 5.1's canonical scene (the camera + controls are created in scene init — `PerspectiveCamera` at WordWeaverScene.js:53, `OrbitControls` at :71) and on 5.2's layout (focus targets come from `monthClusters[i]` world positions and `findDayBlock(m,d)` — WordWeaverScene.js:215-231). It feeds 5.6 (the raycaster turns a pick into a `focusOnDay`/`focusOnMonth` call — WordWeaverScene.js:690 already does this; 5.6 owns the pick, 5.5 owns the resulting camera move) and coordinates with 5.4.5 (decorations stay world-fixed; the camera must not make atoms appear to track the user). It carries the two Phase-5 recurring threads: the **duplicate-renderer / parallel-stack** pattern — here **three** camera/movement subsystems (inline `_cameraFocus` in `WordWeaverScene`, the standalone `CameraController.js` on the 2D wall, and the fly-movement in `WordWeaverTimelineViewport.js`, plus **two** keyboard input paths) — and the **§13.2 event-bus gap** (focus methods emit no `dayFocused`/`monthFocused` and consume no `navigateTo`, the recurring Phase-4/5 finding).

## Current implementation status (reconciliation)

A working camera **already exists and is live in the year ring** — `PerspectiveCamera` + `OrbitControls`, a year-overview framer, `focusOnMonth`/`focusOnDay`, an eased focus animation, desktop WASD/Q-E fly, and a custom mobile overlay. But the **intrinsics diverge** (FOV 42 not 60, far 80 not 2000), the **poses differ** from the spec numbers, the **transition model is time-based easing not the spec's per-frame factor-0.08 lerp**, the focus API is **incomplete** (no `focusOnToday`/`focusOnNextEvent`/`focusOnCategory`, and `focusOnDay` doesn't open the day panel), there are **three parallel camera/movement subsystems and two keyboard input paths**, reduced-motion is **not honored**, and focus emits **no §13.2 events**. This is an upgrade/reconcile + converge milestone, not greenfield.

- **Three parallel camera/movement subsystems; the §11 tree's `CameraController` isn't the one driving the ring.** §11 line 1011 lists `CameraController` under the scene, but the **live year-ring camera move** is **inline** in `WordWeaverScene` (`_startCameraFocus`/`_updateCameraFocus`, WordWeaverScene.js:241-270) — a time-based eased `lerpVectors`. The **standalone** [`CameraController.js`](../../src/calendar/CameraController.js) (`zoomToDay`/`zoomToOverview`/`restoreCamera`, promise-based `easeInOutCubic`, durations 900/800ms) is wired to the **2D-wall** `CalendarApp` (CalendarApp.js:27, 97), **not** the year ring. A **third** subsystem — fly translation — lives in `WordWeaverTimelineViewport.js` (:36-73, moves both `camera.position` and `controls.target`). 5.5.1 picks the canonical camera class/path and reconciles §11; the others are dispositioned (keep `CameraController` for the wall, fold fly-movement into the canonical camera).
- **Intrinsics diverge: FOV 42 (not 60), far 80 (not 2000/1000).** §5.6 line 567 wants FOV 60°, near 0.1, far 2000 (line 487 says far 1000 — an internal spec disagreement to settle); the live camera is `new THREE.PerspectiveCamera(42, 1, 0.1, 80)` (WordWeaverScene.js:53). **Far = 80 is the 5.1.4 ring-clip bug** (at the spec's ring radius ~80 the back of the ring sits up to ~160 units out and is clipped). Near 0.1 ✓ and aspect-on-resize ✓ (`camera.aspect = w/h; updateProjectionMatrix()`, WordWeaverScene.js:634-635). 5.5.2 reconciles FOV/far and settles the 1000-vs-2000 spec conflict.
- **Poses differ from the spec numbers; two competing "home" concepts.** §5.6 line 586-588 wants year overview `(0, 60, 120)` → origin, month ~20 units out, day close-framed. Live: `_frameYearCamera` sets `(0, 18, 42)` → origin with `maxDistance 120` (WordWeaverScene.js:204-208) — much nearer/lower than `(0,60,120)`; `focusOnMonth` uses **distance 14** (not ~20) at height 2.5 (WordWeaverScene.js:219); `focusOnDay` uses distance 5.5 / height 1.2 (WordWeaverScene.js:233). There are **two** home notions: `_cameraHome`/`_targetHome` (WordWeaverScene.js:57-58, `(0,2.4,8.2)`→`(0,1.1,0)`, the *embed* default) **and** `_frameYearCamera`'s year-overview pose — they don't agree on what "overview" is. 5.5.3 reconciles the three poses to the spec and unifies the home concept.
- **Transition model is fixed-duration easing, not the spec's per-frame factor-0.08 lerp + snap.** §5.6 line 590-595 / §23.2 line 1655 specify per-frame `lerpTo(target, 0.08)` on both `camera.position` and `controls.target`, with a **snap when distance < 0.01**. The live `_startCameraFocus`/`_updateCameraFocus` (WordWeaverScene.js:241-270) instead runs a **fixed 850ms** animation with a **cubic-out ease** (`ease = 1 - (1-t)**3`) via `lerpVectors(start, end, ease)` — a *time-based* model, frame-rate-independent (good), but **not** the spec's exponential-approach factor model, and there's **no 0.01 snap threshold** (it ends on `t >= 1`). `CameraController.js` is a *third* variant (900/800ms `easeInOutCubic`). 5.5.4 reconciles: either adopt the factor-0.08 per-frame lerp the spec/§23.2 name, **or** document the time-based easing as a deliberate, superior-feeling improvement and update §5.6/§23.2 to match — pick one, and add the snap/short-circuit.
- **`OrbitControls` is configured but tuned to the embed, not the spec poses.** Desktop controls exist: `enableDamping` ✓, `maxPolarAngle = π`, `minDistance 0.4`, `maxDistance 80`, `enablePan` ✓ (WordWeaverScene.js:71-77), and the frame loop calls `controls.update()` ✓ (WordWeaverScene.js:744, satisfying §16.1 step 1). Default mouse mapping (left orbit / right pan / wheel zoom) is OrbitControls' built-in ✓ (§5.6 line 570-572). But `maxDistance 80` (and the `_frameYearCamera` bump to 120) **collide with the far plane** (5.5.2) and the ring radius — at `(0,60,120)` overview the camera is 134 units out, beyond both. 5.5.5 reconciles control limits with the corrected far plane and the spec overview distance.
- **Desktop keyboard fly exists but via TWO parallel input paths, with Space/Shift not Q/E, and no R reset.** §5.6 line 573-575 wants WASD fly, **Q/E elevate/descend**, **R reset to overview**. Live reality is split: `WordWeaverTimelineViewport.js` (:46-49) reads `KeyW/S/A/D` **and `KeyQ/KeyE`** (vertical) from its own `window` keydown/keyup listeners **plus** `extForward/extStrafe/extLift`; `WordWeaverChrome.js` (:140-153) **separately** tracks `keysHeld` and maps W/S/A/D + **Space/Shift** (not Q/E) to `scene.setFlightInput(...)` → the viewport's `ext*`. So **two** keyboard handlers feed the same motion (risking double-counting W/A/S/D), they **disagree** on the lift keys (Q/E vs Space/Shift), and **no key resets the camera (R)**. 5.5.6 converges to a single input path, standardizes on Q/E (+ keep Space/Shift as aliases if desired), and adds R → `focusOverview`.
- **Mobile uses `OrbitControls` touch + a custom overlay — partially matching the spec's "custom touch handler".** §5.6 line 577 says mobile uses a **custom** handler (not `OrbitControls`). Live: `OrbitControls` still handles touch orbit/pinch/pan (single class for both platforms), **augmented** by `WordWeaverMobileControls.js` — a forward-slide pad, an analog joystick, and Fly/Descend hold-buttons (WordWeaverMobileControls.js:42-58) whose input is summed into `setFlightInput` via `WordWeaverChrome` (:145-150). This **covers** the spec's thumb-slide-fly and fly/descend buttons (lines 581-583) and, through OrbitControls, single-drag-orbit / pinch-zoom / two-finger-pan (lines 578-580) — but it is **not** the spec's standalone `TouchController` (no `OrbitControls` on mobile). 5.5.7 reconciles: either formalize the overlay+OrbitControls combo as the mobile handler (cheaper, working) **or** build the dedicated `TouchController` — and gate/disable OrbitControls' redundant touch zoom if it fights the pad.
- **Focus API is incomplete, and `focusOnDay` doesn't open the day panel.** §5.6 line 597-602 lists five methods. Live has only **two**: `focusOnMonth` (WordWeaverScene.js:214, no panel ✓) and `focusOnDay` (WordWeaverScene.js:226 — sets `focusedDay`, `setProximity(true)`, animates) but it **does not open the day detail panel** (spec line 598 says it should — or per §5.7 line 613 a *second* click opens it; reconcile the click-vs-focus panel rule with 5.6). **Missing entirely:** `focusOnToday` (line 600, today's m/d), `focusOnNextEvent` (line 601, next upcoming event's date), `focusOnCategory` (line 602, next day with a category event). 5.5.8 adds the three missing methods and reconciles the day-panel trigger.
- **Focus emits no §13.2 events and consumes no `navigateTo` — the recurring Phase-4/5 bus gap.** §13.2 line 1418 says a 3D navigation updates `focusedDate` and emits `dayFocused`/`monthFocused`; line 436 says `WordWeaverScene` should *listen* to `navigateTo`. Live `focusOnDay`/`focusOnMonth` set `_yearLayout.focusedDay` but emit **nothing** on the Phase-2 bus, and the scene listens only to `timelineUpdated` on the *duplicate* WordWeaver bus (the 5.1.9 finding) — so a 2D→3D `navigateTo` won't move the camera, and a 3D focus won't update the 2D views or top bar. 5.5.9 wires focus → emit `dayFocused`/`monthFocused` and a `navigateTo` listener → `focusOnDay`/`focusOnMonth`, on the canonical bus.
- **`prefers-reduced-motion` is not honored — accessibility gap (mirrors 5.4.6).** §23.3 line 1664 mandates that under reduced motion **camera transitions snap immediately** (lerp factor 1 for one frame). `_updateCameraFocus` (WordWeaverScene.js:262-269) always runs the full 850ms eased move with no reduced-motion check (the project *has* a probe — `prefersReducedMotion()` in perfFlags.js:6). 5.5.10 makes focus snap under reduced motion, coordinated with the scene-level motion gate (5.1 / 5.4.6).
- **What's already right (keep):** `PerspectiveCamera` + `OrbitControls` chosen ✓ (§5.6 line 567/569); `enableDamping` ✓ (smooth orbit); aspect-on-resize ✓ (WordWeaverScene.js:634-635); `controls.update()` each frame ✓ (§16.1 step 1, WordWeaverScene.js:744); focus targets read from **world positions** of real layout objects (`getWorldPosition` on cluster/block, WordWeaverScene.js:218/231) ✓; an `_animating`-style guard exists (the standalone `CameraController._animating`, and the inline path single-flights via `_cameraFocus`) ✓; fly-movement moves **both** `camera.position` and `controls.target` together so orbit stays sane after flying (WordWeaverTimelineViewport.js:61-72) ✓; mobile overlay provides accessible large-target fly/descend controls ✓ (§27 touch ergonomics); `controls.dispose()` on teardown ✓ (WordWeaverScene.js:774).

## 5.5.4 — Transition model: per-frame lerp factor 0.08 + snap < 0.01 (vs time-based easing)

- **Purpose:** Reconcile the camera-move animation to §5.6 line 590-595 / §23.2 line 1655 — per-frame `camera.position.lerpTo(target, 0.08)` + `controls.target.lerpTo(lookAt, 0.08)` with a **snap when distance < 0.01** — versus the live **fixed-850ms cubic-out** `lerpVectors` (`_startCameraFocus`/`_updateCameraFocus`) and the wall `CameraController`'s 900/800ms `easeInOutCubic`; settle on one model and add the snap/short-circuit and interrupt semantics.
