# Phase 5 — Milestone 5.4: AtomGlyph3D (Expanded)

**Goal:** Specify the decorative ambient atom (`AtomGlyph3D` — §5.5): a **slowly rotating, non-interactive** structure of a central `SphereGeometry(0.3, 16, 16)` (`MeshStandardMaterial`, slight emissive) plus **2–3 `TorusGeometry` rings** of varying radii on randomized axes, each ring rotating at a distinct slow speed (**0.002–0.008 rad/frame**), placed **2–4 per month cluster at the corners/edges of the day grid**, all instances sharing a **single `SphereGeometry` reference + two `TorusGeometry` references** with **materials shared per-color**. Purpose is visual depth / ambient life only — no interactive function. This milestone is grounded against the **already-existing** [`AtomGlyph3D.js`](../../src/wordweaver/timeline3d/AtomGlyph3D.js) (the live year-ring atom, via `createBackground`) and the two **parallel** atom implementations [`AtomGlyph.js`](../../src/wordweaver/AtomGlyph.js) and [`WordWeaverAtomOrbits.js`](../../src/wordweaver/WordWeaverAtomOrbits.js) — so every task reconciles built / gap / next-step, not greenfield. It owns the decorative-atom internals and their cluster placement; it does **not** cover the day tile (5.3), ring assembly / cluster layout (5.2 — which *positions* atoms via `populateMonthCluster` and explicitly **deferred shared-atom-geometry to here** in 5.2.6), camera (§5.6 → 5.5), or raycast/hover (§5.7 → 5.6) — it must simply stay *out* of the pick path (5.4.8).

**Spec alignment:** §5.5 line 554-563 (decorative atom = central sphere `SphereGeometry(0.3, 16, 16)` `MeshStandardMaterial` slight emissive, line 558; **2–3** `TorusGeometry` rings of varying radii at different axis orientations, line 559; each ring rotates at a **distinct slow speed 0.002–0.008 rad/frame** around a **randomized axis**, line 560; **2–4 per month cluster at the corners or edges** of the day grid, line 561; **no interactive function**, line 562; **all instances share a single `SphereGeometry` + two `TorusGeometry` refs via instancing, materials shared per-color**, line 563), §5.3 line 512 (2–4 `AtomGlyph3D` decorations floating around the **cluster perimeter**), §5.3 line 516 (`AtomGlyph3D` objects use a **single shared `SphereGeometry` and shared `MeshStandardMaterial`** — the instance-optimization restatement), §1.4 line 88 (aesthetic choices incl. atom glyphs must **never compromise readability or performance**), §11 line 146 + §11 line 1010 + §28 line 1963 (the canonical path is **`src/wordweaver/AtomGlyph3D.js`** and the tree shows `AtomGlyph3D × 2–4` under each `MonthCluster`), §5.8 line 631 (subtle floating `AtomGlyph3D` elements **outside** month clusters as ambient scene decoration), §16.1 line 1306 (frame-loop step 5 = "Animate `AtomGlyph3D` rotations"), §23.2 line 1656 ("AtomGlyph rotate | Continuous | ∞ | linear"), §23.3 line 1665 (under `prefers-reduced-motion`, **`AtomGlyph3D` rotation is paused**), §27.6 line 1821 (3D continuous motion incl. AtomGlyph rotations **fully paused** under reduced motion).

**Sequencing:** Fourth milestone of Phase 5. It depends on 5.1's canonical scene/material/dispose conventions and on 5.2's cluster layout (5.2's `populateMonthCluster` is where atoms are created and placed; **5.2.6 explicitly deferred shared-geometry + deterministic perimeter placement to this milestone**). It mirrors 5.3's shared-resource discipline (module-level shared geometry/material singletons + a guarded disposer that never frees shared refs — the 5.3.10 lesson applies directly). It feeds 5.5 (camera motion must not make atoms appear to track the user — they stay world-fixed in the cluster) and 5.6 (the raycaster must **exclude** atoms — 5.4.8 is the contract 5.6 consumes). It carries two Phase-5 recurring threads: the **duplicate-renderer / parallel-stack** pattern (here it's **three** atom classes — `timeline3d/AtomGlyph3D.js` live in the year ring, root `AtomGlyph.js`, and `WordWeaverAtomOrbits.js` in the satellite weave — echoing Phase 4's two-week-renderer and 5.1's two-scene findings), and **non-determinism / no-instancing** as the central performance reconciliation (the `Math.random`-driven, per-instance-allocated atoms are the §1.4/§16 risk this milestone closes).

## Current implementation status (reconciliation)

A decorative atom **already exists and is live in the year ring** — but it is a *much heavier* object than §5.5 describes, it is **allocated per-instance with no sharing/instancing**, it is **placed non-deterministically** with `Math.random`, and it **ignores `prefers-reduced-motion`**. There are also **three** parallel atom implementations, only one of which is wired into the Phase-5 year ring. This is an upgrade/reconcile + converge milestone, not greenfield.

- **Three parallel atom classes; the spec path doesn't match the live file.** §11 line 146/1963 and the §11 tree (line 1010) cite **`src/wordweaver/AtomGlyph3D.js`**, but the file that is actually **live in the year ring** is **`src/wordweaver/timeline3d/AtomGlyph3D.js`** ([AtomGlyph3D.js](../../src/wordweaver/timeline3d/AtomGlyph3D.js):6), constructed via `AtomGlyph3D.createBackground(...)` in `populateMonthCluster` ([WordWeaverScene.js](../../src/wordweaver/WordWeaverScene.js):884) and updated/disposed through `WordWeaverYearLayout3D.bgAtoms` (WordWeaverScene.js:957, 1019, 1044-1047). Two other atoms exist and are **not** in the year ring: root **[`AtomGlyph.js`](../../src/wordweaver/AtomGlyph.js)** (a gold rings+nucleus+orbiting-particles glyph, `class AtomGlyph`, no current importer in the year path), and **[`WordWeaverAtomOrbits.js`](../../src/wordweaver/WordWeaverAtomOrbits.js)** (the **satellite-weave** decoration — pink "feminine palette" per-note atoms, gated on `getActivePalette().atomOrbits`, mounted on `weaveGroup` at WordWeaverScene.js:428-429, a *different* subsystem from the §5.5 cluster atom). 5.4.1 picks the canonical class and reconciles the path; 5.4.10 dispositions the other two.
- **Geometry is far over-spec: a 64×64 glass shell + four high-seg wave rings + three electrons, not "sphere(0.3,16,16) + 2–3 tori".** §5.5 line 558-559 wants a simple central `SphereGeometry(0.3, 16, 16)` + **2–3** `TorusGeometry` rings. The live atom (AtomGlyph3D.js:25-103) is a **"premium aqua orb"**: a `SphereGeometry(0.225, **64, 64**)` shell on an expensive `MeshPhysicalMaterial` (`transmission: 1.0`, `thickness: 0.7`, `clearcoat: 1.0`, `ior: 1.45`), **four** `TorusGeometry(r, t, 48, 96)` "wave rings" (`ringSpecs`, 60-65), **plus three** orbiting electron spheres (`SphereGeometry(0.0225,16,16)`, 84-103, each with a **cloned** material). That is dramatically heavier than the spec's lightweight decoration (transmission alone forces a render-target pass; 64×64 + 4×(48×96) tori is a large vertex/triangle budget for an *ambient* element repeated 24–48× across the ring). 5.4.2 reconciles geometry/material toward the spec; 5.4.3 shares it.
- **No shared geometry / no instancing — the headline perf gap 5.2.6 deferred here.** §5.5 line 563 + §5.3 line 516 are explicit: **one shared `SphereGeometry` + two shared `TorusGeometry` refs**, materials shared per-color, via instancing. The code instead calls `new AtomGlyph3D({...})` per atom (WordWeaverScene.js:884), and each constructor **allocates fresh** `shellGeo`, four ring geometries, and an electron geometry, and **clones** an electron material per electron (AtomGlyph3D.js:96 `eMat.clone()`). With **2–4 atoms × 12 clusters = ~24–48 atoms**, that is dozens of distinct geometries + materials that should be a handful of shared refs. 5.4.3 introduces module-level shared singletons (mirroring 5.3's `getSharedDayBlockResources`), the direct realization of 5.2.6's deferral.
- **Placement is non-deterministic `Math.random`, not deterministic grid corners/edges.** §5.5 line 561 / §5.3 line 512 want **2–4 atoms at the corners or edges (perimeter)** of the day grid. `populateMonthCluster` (WordWeaverScene.js:880-895) sets `atomCount = 2 + Math.floor(Math.random()*3)` and randomizes **scale** (`2 + Math.random()*3`), **opacity** (`0.1 + Math.random()*0.1`), and **position** (`(Math.random()-0.5)*9`, `-Math.random()*weekCount*ROW_SPACING*0.4`, `-2.5 - Math.random()*2.5`) — so atoms float at **random interior/behind** positions (z pushed back 2.5–5 units, plus `createBackground` forces `z=-6` by default, AtomGlyph3D.js:122), **not** the cluster perimeter, and the layout **changes every rebuild** (non-reproducible, defeats any cache, and visually unstable across the full-rebuild path of 5.2.8). This is the same determinism+perimeter concern 5.2.6 raised and deferred. 5.4.4 makes placement deterministic and perimeter-anchored.
- **Rotation animation is delta-based "premium" motion, not the spec's per-frame slow-spin on randomized axes.** §5.5 line 560 wants each of the 2–3 rings to rotate at a **distinct slow speed (0.002–0.008 rad/frame)** around a **randomized axis**. The live `update(delta)` (AtomGlyph3D.js:126-169) is richer: it spins the shell (`+= dt*0.35*rotMul`), spins the `ringGroup`, and additionally **scale-pulses each wave ring** (`Math.sin` wave/ripple, 142-153) and **orbits three electrons** (160-168) — motion well beyond "slow ring rotation". It is **delta-time-based** (frame-rate-independent — *good*, keep that property), with a `slowRotation` multiplier (0.18) for the background variant. 5.4.5 reconciles: keep delta-based timing but map to the spec's slow per-frame band, decide which "extra life" (wave pulse, electrons) survives as a deliberate enhancement vs. is trimmed for the ambient/year budget, and assign **per-ring randomized axes/speeds**.
- **`prefers-reduced-motion` is ignored — a hard accessibility gap.** §23.3 line 1665 and §27.6 line 1821 mandate that `AtomGlyph3D` rotation is **paused** under reduced-motion. `update()` (AtomGlyph3D.js:126) has **no** reduced-motion check and always animates; the scene's per-frame `for (const atom of this.bgAtoms) atom.update(delta)` (WordWeaverScene.js:1019) is unconditional. 5.4.6 honors the preference (skip/freeze updates), coordinated with the scene-level motion gate (a 5.1 carry).
- **Per-frame update of every atom; no LOD/cull for far clusters.** Frame-loop step 5 (§16.1 line 1306) is "Animate AtomGlyph3D rotations", but §1.4/§16 demand it not cost readability/perf. The scene updates **all** `bgAtoms` every frame (WordWeaverScene.js:1019) regardless of whether the cluster is near, far, or off-screen — and each update runs shell + 4-ring wave math + 3-electron orbits. With ~24–48 heavy atoms this is avoidable work. 5.4.7 gates updates by cluster proximity/visibility (reusing the per-cluster distance signal the scene already computes for DayBlock proximity, WordWeaverScene.js:1030) and/or freezes off-screen atoms.
- **Non-interactive invariant is not enforced against the (future) raycaster.** §5.5 line 562 = "No interactive function." The atom group is added straight to the cluster (`cluster.add(atom.group)`, WordWeaverScene.js:893) with a generic name `"atom-glyph-3d"` (AtomGlyph3D.js:16) and **no pick `userData`** — so it *currently* won't be picked, but 5.6's raycaster has no explicit exclusion contract yet, and DayBlock3D-style picking keys on `userData.dayBlock`/`name`. 5.4.8 makes the exclusion explicit (`raycast = () => {}` or a `userData.nonInteractive`/layer convention) so 5.6 can't accidentally pick decorations.
- **Dispose works today but becomes a double-free risk after sharing.** Each atom currently **owns** its geometry/materials, so `dispose()` (AtomGlyph3D.js:171-183, traverse → dispose all) and the scene's `bgAtoms` disposal (WordWeaverScene.js:1044-1047) are correct *now*. But once 5.4.3 moves geometry/materials to **shared module-level singletons**, this traverse-and-dispose-everything path would free the shared refs and break sibling atoms — exactly the 5.3.10 hazard. 5.4.9 splits owned vs. shared disposal (guarded) and adds a module-level shared-resource disposer; it also addresses the per-electron `eMat.clone()` leak (cloned materials must be tracked + disposed, or eliminated by sharing).
- **What's already right (keep):** delta-clamped update (`dt = clamp(delta, 0.001, 0.05)`, AtomGlyph3D.js:127) — frame-rate-safe ✓; the `slowRotation` flag + faint low-opacity background variant (`createBackground`, opacity ~0.1–0.2) read as *ambient*, not distracting ✓ (§1.4); `depthWrite: false` on the transparent shell/rings + `renderOrder` layering ✓ (correct transparency); `MeshStandardMaterial` for the rings ✓ (§5.5 line 558-559 material family); count **2–4** ✓ (`2 + 0..2`); a `dispose()` traverse exists ✓ (just needs the shared/owned split); atoms read **no model data** (pure decoration) ✓ (§5.5 line 562 non-interactive intent); `object3d` getter + `group.name` give a stable handle ✓.

## 5.4.5 — Slow ring rotation on randomized axes (0.002–0.008 rad/frame)

- **Purpose:** Reconcile the animation to §5.5 line 560 / §23.2 line 1656 — each ring rotates at a **distinct slow speed (0.002–0.008 rad/frame)** around a **randomized axis**, linear and continuous — while preserving the live code's frame-rate-independent (delta-based) timing, and deciding which of the current "premium" extras (wave-pulse scaling, orbiting electrons) survive.
- **Dependencies:** 5.4.2 (the 2–3 rings being rotated), 5.4.3 (shared/instanced transforms must allow per-ring independent rotation — or this constrains the instancing choice), 5.4.6 (reduced-motion pauses this), 5.4.7 (only near/visible atoms update); §5.5 line 560, §23.2 line 1656.
- **Acceptance criteria:** Each ring rotates continuously at a **distinct** slow rate; the rate is specified as the spec's per-frame band **0.002–0.008 rad/frame** but implemented **delta-based** (rate-per-second = per-frame × ~60, applied as `+= ratePerSec * dt`) so it's frame-rate-independent (the live `dt`-clamp at AtomGlyph3D.js:127 is kept); each ring's rotation **axis is randomized** (deterministically seeded per 5.4.4) and distinct from its siblings; the motion is **linear** (no easing, §23.2); any retained wave-pulse/electron motion is an explicit documented enhancement gated for desktop/near-only (5.4.7), not the §5.5 default.
- **Implementation notes:** In `update(delta)` (AtomGlyph3D.js:126-169): keep the `dt` clamp; set each ring's per-frame increment from a per-ring constant in the 0.002–0.008 band (converted to per-second: ~0.12–0.48 rad/s) applied as `ring.rotateOnAxis(axis, ratePerSec * dt)` with a **randomized (seeded) axis** per ring; **decide on the extras** — the wave-pulse scaling (142-153) and 3 electron orbits (160-168) exceed §5.5's "slowly rotating rings" and add per-frame cost across ~24–48 atoms: default to **removing/disabling** them for the cluster atom (keep them, if at all, only for the focused/near tier on desktop, 5.4.7). Preserve `slowRotation`'s intent (background atoms are *slow*) by living in the low end of the band.
- **Edge cases:** Per-frame constants (0.002–0.008 rad) assume 60fps — the delta-based conversion must hold the same *visual* speed at 30/120fps (verify); randomized axes must be normalized unit vectors; if 5.4.3 chose `InstancedMesh`, per-ring independent rotation may require per-instance matrices updated each frame (a cost trade — document, or fall back to shared-ref non-instanced for animated atoms); reduced-motion (5.4.6) must cleanly freeze without snapping.
- **UI/UX considerations:** Slow, distinct-axis rotation gives "ambient life" (§5.5 line 562) without drawing the eye; fast or synchronized rotation would look mechanical and distracting (§1.4).
- **Data flow notes:** Time/delta in → ring transforms out; axes/speeds seeded from 5.4.4's deterministic per-atom seed.
- **Testing notes:** Each ring rotates at a different rate within 0.002–0.008 rad/frame-equivalent; visual speed is identical at 30/60/120fps (delta-based); axes differ per ring; no easing; with extras removed, the per-atom `update` cost drops to ~2–3 ring rotations.
- **Performance notes:** Trimming wave-pulse + electron orbits removes the bulk of per-frame atom math; the remaining 2–3 `rotateOnAxis` calls are cheap; gating to near/visible atoms (5.4.7) bounds the total.
- **Mobile vs desktop:** Mobile: 2 rings, slow end of the band, no extras; desktop: up to 3 rings, optional focused-tier extras.
- **Integration points:** §5.5 line 560, §23.2 line 1656, 5.4.2 (rings), 5.4.3 (instancing vs per-ring rotation trade), 5.4.6 (pause), 5.4.7 (update gating).
- **Status:** **Partial / over-rich.** Delta-based timing ✓ (keep), but motion is shell-spin + 4-ring wave-pulse + 3-electron orbit, not "2–3 rings slowly rotating on randomized axes"; speeds not mapped to the 0.002–0.008 band. **Next:** per-ring randomized-axis slow rotation in-band (delta-based), trim/gate the extras.
